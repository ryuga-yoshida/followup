## こういう状況はありませんか

デスクワークをされている方なら、一度は見たことがある光景だと思います。

- 会議で決まったはずの作業が、どこにも登録されていない
- 進み具合は担当者に聞かないと分からない
- `売上見込_v3_final_修正_更新版.xlsx` が増え続け、どれが最新か誰も答えられない
- 手順書が古いまま残っている。直せる人はすでに異動している
- 半年前の資料を開いても、その数字になった理由をたどれない
- 据え置きと決めた数字が、翌週の資料では変わっている

原因は、担当者が決まっていない作業が間に挟まっている点にあります。

議事録の確認、進み具合の更新、版の整理、資料の最新化、決定と資料の突き合わせ。
どれも最後に手を動かした人がやるのか、管理者がやるのか、引き継いだ人がやるのかが曖昧なまま残ります。

この部分をまとめて引き受けるアプリとして、**Followup（進行管理エージェント）** を作りました。
利用者が行うのは、決める作業と作る作業のみです。

- コード: https://github.com/ryuga-yoshida/followup

## 利用の流れ

会議から提出までは、人がいつもどおりに進めます。
進行管理は、その裏でエージェントが行います。

![利用の流れ](https://static.zenn.studio/user-upload/cbded02e089a-20260922.png)

| 段階 | 人 | エージェント |
|---|---|---|
| 1. 会議 | 会議室で話し、終了を押す | 話した人ごとに文字起こし |
| 2. 議事録 | 要点を読む | 決定・作業・懸念を取り出し、根拠の発言を引用。Wiki に議事録ページを作成 |
| 3. タスク | 担当と期限を確認し、違えば直す | 作業を登録。担当者を発言から読み取り、決定に紐付け |
| 4. 成果物 | Excel や Word を作り、保存する | 版を採番し、セルや段落の差分を取り、作業に紐付け。決定と突き合わせて食い違いを通知 |
| 5. チャット | URL を貼る、引用して返信する、直しました と書く | どの作業の話かを読み取り、状態の変更を提案 |
| 6. 提出・Wiki | 修正版を保存し、提案を承認する | 成果物のページを最新化。止まっていれば通知 |

4 と 5 は、完了するまで繰り返します。

## 冒頭の状況にどう対応するか

| 状況 | エージェント | 人 |
|---|---|---|
| 作業が登録されていない | 会議の終了時点で決定と作業を取り出して登録。担当者は発言から読み取る | 誤りがあれば直す |
| 進み具合が分からない | チャットの URL・引用返信・メンションから、どの作業の話かを読み取り、状態の変更を提案 | 承認する |
| どれが最新か分からない | 保存のたびに版を積み、差分を取り、作業と根拠の発言に紐付ける | 保存する |
| Wiki が古い | 成果物ごとのページ（最新版・履歴・変更点・関連する作業と決定）を自動で作り、版が増えるたび最新化 | 読む |
| 決定の経緯が追えない | 決定 → 作業 → 発言 → 変更 → 検知 を 1 本の時系列に並べる | さかのぼる |
| 決定と資料が食い違う | 決定と変更を突き合わせ、食い違い・根拠のない変更・停滞を通知 | 確認、却下、作業化 |

エージェントが行うのは通知と提案までです。書き換えは人が承認します。

利用者の操作は、いつもどおりの会議・チャット・保存のみです。
エージェントは 60 秒ごとの巡回と、投稿や保存をきっかけに動きます。

チャット・メール・予定表・会議室・Wiki・成果物の置き場は、入力が本物であるとデモで示すために自作しました。
外部サービスとの接続部分は差し替え前提の作りで、Microsoft Graph などに置き換えても判定の仕組みは変わりません。
現時点でメールと予定表は表示のみですが、Outlook との連動も可能です。

### 決定と資料が食い違う → 人が気づく前に通知

> 決定（見込み表の更新は商品 D の追加と商品 B の修正のみ。それ以外の数字は変更しない）と、
> 変更（売上見込の商品 A の第 4 四半期が 1200 から 1500）が食い違っています。
> 根拠: ① 9/15 定例の発言（原文）② 9/18 のチャットでの共有 ③ セル `売上見込!D5` の差分

![検知カード](https://static.zenn.studio/user-upload/044785bea549-20260922.png)

| 検知の種類 | 内容 | AI |
|---|---|---|
| 食い違い | 決定と成果物の変更が合わない | 使う |
| 根拠のない変更 | どの決定にも紐付かない変更 | 使わない |
| 停滞 | 7 日以上動きのない作業 | 使わない |
| 状態の提案 | 会話から進み具合の変更を提案 | 使わない |

架空データ約 2 週間分では、成果物の変更 30 件のうち通知は 3 件（食い違い 2 件・根拠のない変更 1 件）でした。
残り 27 件は通知していません。人への確認依頼は 0 件です。

## 仕組み

Google Cloud 上で動かしています。アプリは Cloud Run、判定と文字起こしは Gemini API です。

![アーキテクチャ](https://static.zenn.studio/user-upload/47cff6b03a12-20260922.png)

### 5 つの入り口を、同じ形の記録に直す

チャット・メール・会議・Wiki・成果物の 5 つを、同じ形の記録に変換してから保存します。
決定・作業・発言・変更がすべて同じ形で並ぶため、議事録の作成も、進み具合の追跡も、食い違いの検知も、同じ場所への処理になります。
入り口を増やすときは、変換部分を 1 つ足すだけで済みます。

![同じ形の記録に直す](https://static.zenn.studio/user-upload/fd0a324db828-20260922.png)

### 食い違いの見つけ方（AI を呼ぶのは最後だけ）

候補の絞り込みと、明らかに対象外の除外は、AI を使わずに処理します。
AI に渡すのは、絞り込んだあとの 1 組だけです。

判定の答えには、決定と変更の対象が同じかどうかを必ず含めさせます。
別物であれば、数字が合わなくても食い違いとして扱いません。
処理は増えた分だけに限り、毎回すべてを見直すような動きはしません。

![食い違いの見つけ方](https://static.zenn.studio/user-upload/0afc2d04b9c4-20260922.png)

### 壊れたときの振る舞い

| 事象 | 挙動 |
|---|---|
| AI の応答が壊れている、または時間切れ | その 1 件を飛ばし、次回やり直す。通知はしない |
| 取り出した引用が発言の原文に無い | 作り話として捨てる |
| 判定に自信がない | 食い違いなしとして返すか、確信度 0.4 以下で返す |
| 再起動 | 同時書き込みの設定と、Cloud Storage への退避から復元 |

検知のカードには、必ず出典を 3 点表示します。根拠が 2 件未満の検知は、保存の時点で弾かれます。

## 精度の確認

正解を付けた 10 件（食い違いあり 6・通知してはいけない 4）を用意し、判定を変えるたびに再生して確かめます。
結果は **9/10 検知・誤検知 0・見逃し 1**（数式だけの変更）です。

途中は 8/10・誤検知 1 でした。
在庫表の商品 A の変更を、売上見込についての決定と突き合わせてしまったのが原因です。
対象が同じかどうかを、表・商品・指標の 3 点で判定させる指示に変えて解消しました。

## モデルの使い分けと料金

AI の呼び出しは、すべて Gemini API に直接出しています。
呼び出す回数が多い処理ほど軽いモデルに回し、食い違いの判定だけを上位のモデルに残しました。
議事録の作成、Wiki の生成、差分の取得、紐付けの前半は AI を使いません。

![モデルの使い分けと実測の料金](https://static.zenn.studio/user-upload/8611ab6c603c-20260922.png)
![コスト画面](https://static.zenn.studio/user-upload/7e5efa6eed3d-20260922.png)

判定を上位のモデルに残した理由は、対象が別物かどうか、後の決定で上書きされていないかどうかの読み取りが、軽いモデルでは安定しなかったためです。

応答は送った文面をかぎにして保存しているため、再生のときは保存済みの応答だけで動きます。
API キーなしで同じ結果を再現でき、画面の開発中にかかった料金は 0 でした。

## 安全のための対策

| 事象 | 懸念点 | 対策 | 確認できる画面 |
|---|---|---|---|
| 個人情報の流出 | 判定のために送る会話に、氏名・メールアドレス・電話番号が含まれる | 送る前に伏せ字へ置き換え、応答を受け取ってから元に戻す。送るのは判定に必要な発言のみ | エージェント画面の送信内容 |
| エージェントの乗っ取り | 議事録やチャットに、指示を上書きする文面が混ざる | 議事録の本文は指示ではなく資料として区切って渡す。取り出した結果は、引用が原文にあるかを機械的に照合 | 架空データに混入済み。取り出しに漏れないと画面で確認できる |
| 作り話 | 会議で出ていない作業を AI が作る | 引用が原文に無い作業は捨てる。検知は出典 3 点がそろわないと保存できない | 作業詳細の根拠欄、検知カードの出典 |
| 誤った自動変更 | エージェントが勝手に書き換える | エージェントは通知と提案まで。適用は人が承認する。エージェントが作った Wiki は判定の対象から外す | 状態の提案、Wiki の編集者欄 |
| 権限外の操作 | 閲覧のみの利用者が設定を変える | 管理者・一般・閲覧の 3 役割。全リクエストを記録。外部連携は読み取り専用のみ | 設定のユーザー、監査ログ |
| 秘密情報の流出 | API キーやパスワードがコードに残る | `.env` と Secret Manager のみに置き、リポジトリには含めない | リポジトリに置いてあるのは記入例のみ |

## つまずいた点と対処

| 発生場所 | 事象 | 原因 | 対処 |
|---|---|---|---|
| 会議からの作業の取り出し | 1 回の会議から 37 件が登録された（実際は 8 件） | 会議の最後の読み上げを、本編と別の作業として二重に取り出していた | 文章の近さで同じ作業をまとめる。チャットからは自動で作らない |
| 文章の近さを測る API | 呼び出しが 400 で止まった | 1 回 100 件までの上限と、空文字を渡せない制約 | 100 件ずつに分け、空文字は飛ばす |
| 応答の再生 | 同じデータなのに毎回 AI を呼び直していた | 送る文面に、作り直すたびに変わる管理番号を入れていた | 文面の中の参照を連番に変更 |
| 画面への通知 | 巡回側から送った通知が画面に届かない | 別の処理系統から送っていたため、画面側と別の接続になっていた | 起動時に本体側を保持し、そこへ渡して送る |
| データベース | 読み書きが詰まって画面が固まった | 毎回テーブル定義を実行しつつ、画面の更新と巡回が同時に書き込んでいた | 同時書き込みの設定を入れ、テーブル定義は起動時の 1 回のみに変更 |
| git | 1.8GB の添付を登録してしまい、送信が止まった | アップロードの上限がなく、添付の置き場が管理対象に入っていた | 上限を 50MB にし、添付の置き場を管理対象から外す |

## まとめ

- 5 つの入り口を同じ形の記録に直し、1 か所にまとめて扱います
- AI を使うのは取り出しと最後の判定のみで、議事録・差分・紐付け・Wiki・時系列・引用の照合は AI を使いません
- モデルの使い分けで $0.14 に収まりました。すべて上位モデルで処理した場合の 44% 減です
- エージェントは書き換えません。承認するのは人です
